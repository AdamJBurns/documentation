- **Site values** for the helmfile (`deploy/selfhost/environments/default.yaml`, copied to your own file).
  They describe the site and are turned into values for each chart.
- **Chart values** of `deploy/helm/atoll`. The helmfile sets them in `deploy/selfhost/values/atoll.yaml.gotmpl`;
  override any of them with `atoll.values` in your site file.

### Feature settings

Each platform feature reads its own `ATOLL_<AREA>_*` variables. The chart passes them through without knowing
them, so new settings need no chart change:

```yaml
features:
  auth:
    config:                       # plain values; keys must start with ATOLL_AUTH_
      ATOLL_AUTH_GITHUB_CLIENT_ID: Iv1.abc
    existingSecret: atoll-auth    # every key becomes an env var (client secrets, SMTP password)
  env:
    keysSecret: atoll-env         # holds ATOLL_ENV_KEYS=k1:<openssl rand -base64 32>, always required
  domains:
    clusterIssuer: letsencrypt    # ATOLL_DOMAINS_CLUSTER_ISSUER
  billing:
    prometheusUrl: http://kube-prometheus-stack-prometheus.monitoring.svc.cluster.local:9090  # ATOLL_BILLING_PROMETHEUS_URL
    existingSecret: atoll-billing
  git:
    existingSecret: atoll-git
```

The chart refuses a `config` key without the area's prefix, which catches typos.

### Panel host

The panel signs in with the `atoll_session` cookie, set host-only on the panel host (`Secure` when
`urls.panel` is https), and calls `/api` on that same host. Two rules follow:

- The panel host (and the API host) must not be `urls.appsDomain` or below it. Apps under the wildcard run user
  code and could set cookies for a parent domain they share with the panel. The chart fails the install
  otherwise. Prefer an apps domain on a different registrable domain altogether.
- If the panel gets its own host (`urls.panel` different from `urls.public`), the chart adds it to the
  `atoll-server` Ingress. atoll-server serves the panel's static files itself, so by default the whole host
  goes to it; `ingress.panelService` can send everything but `/api` to a separate Service instead.

Behind the ingress the server trusts `X-Forwarded-For`/`-Proto` (`ATOLL_AUTH_TRUST_FORWARDED=true`) for
client IPs (rate limits, audit) and the https scheme. That is safe because Traefik overwrites those headers
from clients it does not trust, and the `atoll-server` NetworkPolicy keeps everything but the controller and
the release namespace away from the API port. Build pods run untrusted code and could send any header, so they
only reach the internal port 8081, which serves the build protocol (`/internal`) and nothing else; `/internal`
in turn answers 404 on the API port.

### Network policies

| Policy | Effect |
|--------|--------|
| `atoll-builds` | Build pods accept nothing; egress only to DNS, atoll-server:8081 (build protocol), the bundled registry, the ingress controller (`networkPolicy.builds.allowIngressController`, needed when the registry is behind it) and port 443 on public IPs |
| `atoll-apps` | App pods accept traffic only from the ingress controller namespace (8080, and 8089 for cert-manager solvers) and, with scale to zero, KEDA's interceptor (8080). Egress: DNS, the ingress controller (`networkPolicy.apps.allowIngressController`) and any port on public IPs; never private ranges, CGNAT, link-local (cloud metadata `169.254.169.254`), loopback or multicast |
| `atoll-server` | Port 8080 (API) accepts its own namespace, the ingress controller and `networkPolicy.server.extraNamespaces`; port 8081 (build protocol) only build pods |
| `atoll-postgres`, `atoll-storage` | Bundled database and storage accept only the server |
| `atoll-stores` | Users' stores accept their own namespace, the server (5432, 6379, 8333), the CloudNativePG operator (5432, 8000), monitoring (metrics) and, on the Files S3 port 8333, app pods and the ingress controller. Postgres and Redis admit connected projects' app pods through per-store policies the server keeps; `atoll-apps` egress allows the storage namespace on 5432, 6379 and 8333 |
| `atoll-registry` | Bundled registry accepts build pods and, with `nodeAccess`, the listed node CIDRs |
| `atoll-db` (helmfile) | CloudNativePG accepts the server, its replicas, the operator and Prometheus |
| SeaweedFS (helmfile) | Components accept each other; from outside only S3 (8333) from atoll-server and zot, and metrics from Prometheus |
| `zot` (helmfile) | Only the ingress controller (pushes and node pulls both go through Traefik) |
| `monitoring-*` (helmfile) | Monitoring pods accept only Grafana, Prometheus, Alertmanager and Alloy; Grafana also the ingress controller, Prometheus also atoll-server (billing). The operator is left open for the API server's webhook calls. Loki runs without multi-tenancy, so tenants must never reach it |

k3s enforces them with its built-in controller. Other clusters need a CNI that enforces NetworkPolicies.
Egress is restricted for build and app pods (untrusted code); platform components keep open egress.

### Ingress controllers

Traefik is the default. Two details are handled by the chart:

- Traefik ranks routers by rule length, and the wildcard rule `*.apps...` is longer than short exact hosts, so
  the wildcard `atoll-sites` Ingress gets `router.priority: 1` and app Ingresses always win.
- App Ingresses have TLS without a secret. A Traefik `TLSStore` named `default` serves the wildcard certificate
  for them (`certManager.traefikDefaultCertificate`).

With `ingress.controller: nginx` the chart adds ingress-nginx annotations (512m uploads, 300 s timeouts)
instead; set the wildcard certificate as `--default-ssl-certificate`. ingress-nginx no longer gets security
fixes, so prefer Traefik.
